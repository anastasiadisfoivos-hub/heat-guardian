3. DEFECTS (ranked)
=====================================================================================
BLOCKER
B1 A run of resets deletes the undumped 1 Hz history.
   Why: setup() calls newHourFile() on EVERY boot (08_logger.ino:1269), which calls
   ringMakeRoom(.., HG_RING_MAX_S_FILES = 20). The ring limits s-files BY COUNT (log_ring.c
   hg_ring_plan, need_count). So every reset adds a new short file, and each file past 20 deletes
   the oldest FULL hour file.
   Repro: t6a/test_reboot_ring.c, driving the real log_ring.c from the builder's own 3-day steady
   state (17 full hour files):
     5 resets  -> 2 h lost
     20 resets -> all 17 h lost; 200 s of 1 Hz data left on flash
   (t6a/reboot_ring_result.txt).
   Triggers that are realistic on Nov 16-18:
   - a brown-out cycle when the 250 mAh cell runs flat overnight;
   - a watchdog loop from an intermittent hang (M2, or the builder's own "littlefs assert reboot
     loop" risk).
   Also, each ordinary reset (button, re-plug) costs ~1 h of retention.
   min.bin survives (minute means only).
   Fix direction (builder): on boot, keep appending to the newest s-file while it holds < 3600
   records (the boot marker is enough); limit the ring by free space only, not by count. Add a
   reset-loop guard: if 3 or more boots happen within 10 min, make no new file and do no deletions.

MAJOR
M1 The reset reason is always 0, so the watchdog counter is blind.
   Why: the core's init() (cores/nRF5/wiring.c:37-40) saves and CLEARS NRF_POWER->RESETREAS before
   setup(). The sketch's read at 08_logger.ino:1219 therefore always sees 0.
   Effects: every boot is named "POWER-ON/BROWN-OUT", bootf.wdt_resets never increments, and
   other_resets counts every boot.
   The README's Monday check "resets: watchdog=0 = no crashes" can never fail.
   Fix: resetReason = readResetReason(); (wiring.c:72).

M2 I2C has no timeout, so a loose Qwiic plug can stop all logging.
   Why: Wire_nRF52.cpp lines 171-252 are unbounded while(!EVENTS_...) loops. TWIM waits forever
   while SCL is held low (clock stretching). SETUP.md documents exactly this fault: a half-in plug
   "drags SDA/SCL LOW".
   The comment at 08_logger.ino:245 ("bounded: no library loops that can spin forever") is false.
   Result: a hang -> watchdog reset -> setup() hangs again in the sensor probes (lines 1235-1244),
   which run BEFORE storageInit() and bleSetup(). The band then records nothing and advertises
   nothing until the plug is fixed. Only a 1-line USB banner shows it.
   Fix direction: check that SDA and SCL read HIGH and do a 9-clock bus clear before Wire.begin();
   init storage and BLE and write the BOOT event before the sensors; after 2 watchdog resets in a
   row, skip the I2C device that was being probed (stored in retained RAM).

M3 The QSPI peripheral stays active between flushes, which costs battery that is not in the
   ESTIMATE.
   Why: nrfx_qspi.c:156 activates QSPI in begin(), and it is deactivated only in uninit (line 335),
   which the sketch never calls. flashSleep() only puts the CHIP in deep power-down.
   Nordic DevZone thread 64145 (customer measurement): +0.7 mA in run mode after nrfx_qspi_init,
   ~1.6 mA vs <0.4 mA in sleep. Nordic erratum 122 applies.
   This is roughly +20-30 % on the 2.5-3.5 mA ESTIMATE (UNVERIFIED without a board).
   Fix: after the 0xB9, call qspiTr.end() with the erratum-122 writes; call begin() again in
   flashWake().

MINOR
m1 "mark oral 36,85" (decimal comma, Greek habit) -> atof = 36.00 and it is ACCEPTED and stored
   as 3600. This silently corrupts the exam's oral label. Fix: accept ',' and echo the stored

m2 README "storage=CORRUPT ... If not [dumped], try dump first": dump refuses when the storage is

m3 The JEDEC ID is not printed when the flash is not detected. Another chip revision would show

m4 "time" with no argument -> "unknown command: time" (argc check falls through). It should say
   "time needs <unix>".
m5 "format YES" works while the storage is OK (only the help text says "only if CORRUPT").

m6 After any reset, the clock is gone until the next "time" command. Records for that boot have no

m7 One failed TMP117 read sets hasSkin=false, so T1 is absent for up to 60 s until the re-probe

5. "DUMP EVERY 16 h": A SAFER DESIGN (recommendation only, not implemented)
=====================================================================================
The 24-B 1 Hz record repeats the slow channels:
 - T1/T2 change every 5 s and Tair/RH every 10 s: 9 of the 24 B are copies.
 - dc8/aux are needed only for the contact check.
Proposal:
 - A 1 Hz "fast" record of 10 B: t delta u16, HR, hr_q, PI u16, a_std u16, z, flags|marker, crc8.
 - Plus a 24-B "slow" record every 5 s (temps, RH, red DC, battery).
Retention scales as 24 B/s divided by the new rate (today's 24 B/s holds ~17-20 h):
 - 10-B fast + 24 B every 5 s = 14.8 B/s -> x1.6 -> ~28-32 h.
 - 8-B fast record (PI as u8) + 24 B every 10 s = 10.4 B/s -> x2.3 -> ~40-46 h.
   One dump per day is then safe, with margin.
Add "dump new": stream only files not yet dumped (a sequence watermark in boot.bin). That cuts
the nightly dump from minutes to seconds.
With B1 fixed, the deletion order stays oldest-first by space only.

R2.6 NEW DEFECTS (all MINOR; none blocks Monday)
-------------------------------------------------------------------------------------
n1 The "no deletions for 30 min after 3 quick resets" rule never fires for watchdog, pin or brown-out
   resets.
   Why: GPREGRET/GPREGRET2 are RESET by watchdog, pin, brown-out and power-on resets. Only CPU lockup
   and soft reset keep them. Sources: the nRF52 PS reset-behaviour table (nRF52810 PS "Retained
   registers" column; same family) and Nordic DevZone 54465 for the nRF52840 ("The GPREGRET registers
   are not preserved across a watchdog reset").
   The comment at 08_logger.ino:1408 ("survives soft and watchdog resets") and README line 178
   ("after 3 quick resets ... deletes nothing for 30 minutes") are wrong.
   Impact: none on data, because the append path alone keeps every hour (R2.4 B and C ran with no
   effective hold). Uploads (soft resets) do count, so 3 IDE uploads within 10 min print "BOOT-LOOP".
   Fix: keep the counter in boot.bin, or drop the rule and fix the text.
n2 A boot that lives less than 60 s puts none of its 1 Hz records on flash (secBuf is flushed once a
   minute; R2.4 C: 30 s boots -> 0 records). The BOOT event is still written.
   Optional fix: flush at 10 s and 30 s of uptime.
n3 Events logged from inside a flash erase can be lost.
   Why: ppgService() runs inside lfsErase(), and on 3 PPG failures devResult() calls evLog(). evLog()
   appends to evBuf while flushAll() is writing evBuf, and flushAll() then sets evLen=0, dropping the
   new line. It is still echoed live. Rare.
